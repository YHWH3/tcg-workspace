# Workspace

A local-first, self-hosted mini-Notion for a small team (≤7 members). Pages with a block editor (text + image/video/audio/PDF/task-list media blocks), multiple kanban boards with custom stages and drag-and-drop, media-rich task cards, a quick-capture sheet for photo + voice memos (auto-transcribed), infinite-canvas moodboards, `@` page/person mentions with backlinks, comment threads on anything, live presence + instant sync, public read-only share links, and an activity feed — all offline-capable, syncing through a Cloudflare Worker + D1 (+ a Durable Object for presence), installable as a PWA with an Android share target.

## Stack

- **Client:** Vite + React 19 + TypeScript (strict), Tailwind v4, react-router, Dexie (IndexedDB outbox + local blob store), fractional-indexing, @dnd-kit, vite-plugin-pwa (injectManifest custom service worker)
- **Server:** Cloudflare Worker (Hono) + D1 (SQLite) + a SQLite-backed Durable Object (`LiveRoom`) — per-field last-write-wins sync via HLC timestamps; files stored as D1 chunks; Workers AI for voice-memo transcription
- Single npm package; `@cloudflare/vite-plugin` runs the Worker inside `vite dev`.

## Local development

```bash
npm install
npm run db:migrate:local   # create tables in local D1
npm run dev                # http://localhost:5173
```

First visit shows "Create workspace admin" — the first account needs no invite and becomes admin. After that, new members need an invite code generated by an admin in **Settings → Invite codes** (7 seats total).

## Deploy

```bash
npx wrangler login
npx wrangler d1 create workspace-db       # copy the printed database_id
# → put that id into wrangler.jsonc d1_databases[0].database_id
npx wrangler d1 migrations apply DB --remote
npm run deploy                            # vite build + wrangler deploy
```

Deployed at **https://workspace.teqlume-platform-ui.workers.dev** (worker name `workspace`; if taken on your account, rename to `team-workspace` in `wrangler.jsonc`).

Learnings:
- `wrangler d1 create` and `migrations apply --remote` prompt interactively — both accept CI-friendly fallbacks in non-interactive shells.
- The first signup on a fresh deployment becomes the workspace admin — open the deployed URL and create it before anyone else does.
- Read-only sanity checks after deploy: `GET /api/auth/status` → `{"needsBootstrap":true}`, `/` and `/some/deep/route` → SPA HTML, `/manifest.webmanifest` and `/sw.js` → 200, unauthenticated `POST /api/sync/push` → 401.

## AI connectors (MCP)

The Worker exposes an MCP server at `POST https://<host>/mcp` (Streamable HTTP, OAuth 2.1 + PKCE + dynamic client registration). Connect an AI app, sign in with your workspace credentials on the consent page, and it can read and create pages, boards (with custom fields), tasks, mood boards and comments; activity is attributed "via <app>".

Setup per client:

- **Claude**: Settings → Connectors → Add custom connector → paste the MCP URL.
- **ChatGPT**: Settings → Apps & Connectors → Advanced → enable Developer mode → Create. Caveat: write tools require a Business/Enterprise/Edu workspace — Plus/Pro accounts get read-only `search`/`fetch`.
- **Gemini**: gemini.google.com → Settings → Connected Apps → Add a custom app (custom apps currently require a US personal account, English language).
- Any standard MCP client: register via `/register`, then the normal OAuth flow.

Settings → AI connectors shows the URL to copy, per-client steps, and your connected apps with Revoke (revoking kills the grant's tokens immediately). AI changes are undoable from Activity — entries carry an Undo button, the 'AI changes' chip filters to connector writes, and Settings → Recent AI changes lists the last 20 change sets with Undo.

## Website inbox (The Common Ground)

The Common Ground website's form relay forwards every form submission and patron event (`patron.applied`, `approved`, `paid`, `minted`, `refund_needed`) to `POST https://<host>/api/ingest/website`. Each event becomes a record in the built-in **Website inbox** database. The record has these fields:

- Status: New, In review, Replied or Done;
- Source, Email, Page and Event;
- Patron tier, Edition and Application id.

The answers form the record's body. Admins get an Inbox notification for each event. Later patron events with the same `application_id` update the same record: they set the Event, Edition and Tier fields and append a line with the amount, edition, token and tx. They never change the title or Status the team has set.

Settings:

```bash
npx wrangler secret put WEBSITE_INGEST_SECRET   # shared with the relay's FORWARD_SECRET
```

Also set `WEBSITE_INGEST_ENABLED=1` as a plain-text variable (Workers dashboard → Settings → Variables, or `vars` in `wrangler.jsonc`). Without both settings the endpoint answers 503. For local development, put the two settings in a `.dev.vars` file. Never commit that file.

Request contract:

- `X-TCG-Timestamp`: unix seconds, which must be within ±300 s of the server's clock.
- `X-TCG-Signature: sha256=<hex>`: HMAC-SHA256 with the secret over `<timestamp>.<raw body>`.
- The body is JSON:
  - `id` (1–64 chars), the idempotency key;
  - `event`;
  - `occurred_at` (ISO 8601);
  - optional `form_id`, `subject`, `page` and `reply_to`;
  - `answers`: up to 40 `{name, label, value}` items, with string values of at most 5,000 chars;
  - `patron`: `{application_id, tier, currency, amount_display, edition, tx, token_id}`, required for `patron.*` events.
- Responses:
  - 200 `{ok, id, recordId, action}`;
  - 400 when the body fails the schema;
  - 401 for a bad or expired signature;
  - 409 when the same `id` arrives with a different body;
  - 413 over 64 KB;
  - 503 when ingest is not configured, or `{retryable:true}` when the write did not land.
- Retries: the same `id` with the same body returns the first result, even when it is re-signed with a new timestamp. 400, 401, 409 and 413 are final. Retry 503 and other 5xx responses.

The website's `thecommonground.living/notion` redirect may point at the app root or keep the prefix. Either way, `/notion/boards/x` lands on `/boards/x`, and signed-out visitors see the sign-in screen at that URL.

Known limit: while per-space access control is enabled, the `website` writer is not a workspace member, the same as public forms. Ingest then answers 503 and the relay keeps retrying.

## Storage & files

- Files live in D1 (`files` + `file_chunks` tables, 1 MiB chunks) — no R2 needed.
- Limits: **20 MB per file**, **450 MB per workspace** (server-enforced; usage bar in **Settings**).
- Uploads are chunked and resumable; everything attaches offline first and uploads on reconnect.
- Voice memos are auto-transcribed via **Workers AI** (`@cf/openai/whisper-large-v3-turbo`, `ai` binding `AI` in `wrangler.jsonc` — free daily allowance, no key needed). Chrome/Android record `audio/webm`, Safari/iOS `audio/mp4`; both are accepted.
- Android: the PWA manifest registers a `share_target`, so photos/videos can be shared from the gallery straight into the capture sheet (custom service worker stores them in IndexedDB and opens `/capture`).

## Presence, shares & mentions

- A `LiveRoom` Durable Object (WebSocket hibernation) keeps presence per path and pushes `{t:'changed'}` pokes after every sync push, so remote edits land in ~1–2s instead of the 60s fallback poll. WS auth uses the `ws-auth` subprotocol — no tokens in URLs.
- **Share** on any page publishes `/s/<token>` — a read-only render of that page and its sub-pages (blocks, images, PDFs, embedded task lists). Files outside the shared tree return 404; revoking the link shows a friendly "no longer active" page. Public routes are `noindex` and never touch auth or sync.
- `@` opens a mention picker (pages and people; the last entry creates a page). Stored as `@[page:ID]`/`@[user:ID]` tokens that resolve live, so renames propagate and backlinks appear in the target page's "Linked from" section.

## Notes

- Invite codes are single-use; user cap is enforced server-side at redemption.
- All content lives in a generic `records` table (`data` JSON + per-field timestamps); soft delete is a `deleted: true` field that participates in LWW.
- To rename the app, edit `APP_NAME` in `src/core/config.ts` and the manifest in `vite.config.ts`, then re-run `npm run icons` if you want a different monogram.
